# Food Reservations Frontend

Phases 1-6 provide React/TypeScript routing, a responsive staff workspace, admin/token sign-in/session handling, business formatting, maintainable foods/variants, reservations, a business-date dashboard, fulfillment, deposits/refunds, printable order summaries, ingredients/stock movements, purchases, comparable price history, and per-variant recipes with backend-calculated ingredient estimates. Phase 7 adds a planning view of what to cook and which ingredients fall short, summarised on the dashboard, a printable shopping list, and preparation recording that deducts actual ingredient usage after a review. Orders and inventory support filters, URL pagination and scroll return, authoritative review, retained failures/conflicts and uncertain-save reconciliation. A page that fails to render is contained in the workspace content area with a Try again action; navigation stays usable. The workspace is verified with fixtures, not ready for real data until the live gates close.

## Requirements and Setup

Use Node.js 22.12 or newer and npm. The lockfile pins the tested dependencies.

```powershell
npm ci
```

If npm reports that the esbuild install script needs approval, review it with `npm approve-scripts esbuild`. Vite needs to launch its build worker; a restricted execution environment may require permission to run that process.

## Explicit Development Fixtures

```powershell
npm run dev:fixtures
```

Open the URL Vite prints, normally `http://127.0.0.1:5173`. If that port is occupied Vite chooses another one. Temporary fixture username: `admin`; fixture token: `local-admin-token`. The form prefills `admin` and masks the token until revealed. These are synthetic development credentials, never a live backend secret. Sessions live only in memory and a page reload signs out. The fixture label and provisional currency/timezone remain visible.

The fixture transport supports auth/session/settings, menu categories/foods/variants, order queries/details/quotes/create/edit, sequential fulfillment/cancellation, payment/refund entries, the dashboard, ingredients/stock movements, normalized purchases/receipts/price history, recipes/estimates, planning, preparation previews/records/corrections and shared operation reconciliation. Example foods/prices are provisional, including a synthetic development-only stick example; unconfirmed Pork BBQ options are omitted. Menu, orders, inventory, ledger entries, previews, operations and sessions are in memory and reset on reload. Orders start empty. The fixture preview opens with lorem ipsum placeholders standing in for recipes the business has not supplied: ingredients Lorem, Ipsum, Dolor and Amet, one receipt from "Lorem ipsum supplier" (DEV-P0001) that prices them, and a one-unit recipe with a complete estimate for each of the six provisional variants. They are not real recipes; every recipe page in fixture mode is labelled as sample development data, and placeholders can be edited or replaced like any other entry. Automated tests use the same fixture transport without placeholders unless a test asks for them. No live menu, inventory or recipe seed is supplied. Preparation recording is a capability that a fixture transport enables on request: the fixture preview enables it, so orders created there carry prepared quantities and need recorded preparation before they can be marked ready, while automated tests leave it off unless a test asks for it. Production builds exclude fixture accounts/data and fixture-only Temporal/decimal.js calculations. Requests have no implicit fallback from live mode to fixtures.

## Live Backend Configuration

Default `npm run dev` uses live requests to `/api/v1` and proxies `/api` to `http://127.0.0.1:8000`. The [backend](../backend/README.md) implements sign-in, sessions, business settings, the menu, orders with the dashboard, fulfillment steps, cancellation, payments and refunds, ingredients, stock movements, purchases, recipes and ingredient cost estimates, planning, the shopping list, preparation recording and corrections: follow its setup, start it on port 8000, and `npm run dev` signs in as `admin` with the token its setup command printed. Its local setup leaves preparation recording off, as the fixtures do by default; the backend README says how the operator turns it on. `npm run dev:fixtures` still works without any backend. Optional `.env.local` settings:

```dotenv
VITE_API_MODE=live
VITE_API_BASE_URL=/api/v1
API_PROXY_TARGET=http://127.0.0.1:8000
```

Restart Vite after changing environment settings. Do not put secrets into `VITE_` variables; they are browser-visible. The backend must implement [auth/session/settings](docs/phase-0/API_CONTRACT.md#auth-and-settings-phase-1), [menu](docs/phase-0/API_CONTRACT.md#menu-phase-2), [order/quote](docs/phase-0/API_CONTRACT.md#orders-and-quotes-phase-3), [status/payment](docs/phase-0/API_CONTRACT.md#status-and-payments-phase-4), [inventory/purchase](docs/phase-0/API_CONTRACT.md#inventory-and-purchases-phase-5), [recipe/estimate](docs/phase-0/API_CONTRACT.md#recipes-and-cost-estimates-phase-6), and [planning contracts](docs/phase-0/API_CONTRACT.md#planning-and-preparation-phase-7), including cookie sessions, CSRF, permitted actions, versions, durable operation keys/lookups, atomic stock changes, append-only ledgers and immutable snapshots. Workflow access requires its capability; purchases require both inventory and purchases; recipes require menu, recipes and inventory. Live inventory and recipes require confirmed currency/timezone; live reservations also require the other business settings and confirmed selling data. A same-origin deployment must route `/api` to FastAPI and serve `index.html` for application routes including `/account`, `/menu`, `/menu/:foodId/variants/:variantId/recipe`, `/orders/:id`, `/orders/:id/print`, `/dashboard`, `/planning`, `/planning/shopping-list`, `/ingredients/:id`, and `/purchases/:id`, plus their lists.

The temporary sign-in request is `{ username: "admin", token: "<provided token>" }`. A live backend must validate its own configured token and issue the existing cookie session. The fixture token is accepted only by the explicit development transport and is excluded from production JavaScript.

Session polling is read-only and does not extend idle expiry. The frontend rechecks on focus and at the backend-declared deadline, clears protected state when the session ends, and never automatically queues/replays mutations. Session, quote and preview deadlines are compared on the server clock taken from each response's `Date` header, so a wrong device clock does not end them early; without that header the device clock is used. Uncertain remote sign-out blocks reentry until explicitly confirmed. Session storage retains only a pending-sign-out flag and unresolved menu/order/inventory operation UUIDs; no tokens, customer information, supplier notes or drafts are stored.

Menu saves keep input after rejection. A stale version shows the latest saved values and requires explicit draft resolution. An uncertain save blocks another attempt until a read-only status check resolves it. A 404 can enable an explicit retry of the exact original body/key only while that request survives in memory. Closing an editor with an unresolved save asks for confirmation; the editable draft is then discarded, but the exact request is kept in memory (never in browser storage) so the page banner can still check it and, after a 404, retry it. The same applies to order, transaction and inventory saves. After reload/expiry, the UUID survives but the request does not: unresolved/unknown operations require backend/operator reconciliation before new saves. Development fixture storage is not durable, so a reload can intentionally leave an unresolvable operation until the development tab session ends; live storage must implement durable lookup.

Order entry uses configured business dates/times, not browser-local conversion. Ambiguous DST times require an explicit occurrence; nonexistent times are rejected. Quotes supply line totals, delivery, tax, total, balance, and credit. Changes, errors, and expiry invalidate the current review. Existing lines retain their saved names/units/prices even if the menu changes. A saved delivery order opened after delivery has been disabled shows a notice, offers only enabled methods and cannot be reviewed until another method is chosen. A separate review confirms a pending order. Backend-requested customer credit requires acknowledgment, followed by a separate refund where appropriate. Dirty orders/transactions are guarded against dismissal, reload, and history navigation. Operation lookup backs off for at most 30 seconds while processing, then requires another explicit check; it never automatically repeats a mutation.

Order details offer only the next fulfillment step and permitted cancellation/financial actions, with visible unavailable reasons. Ready/completion use staff attestation while preparation recording is disabled; unpaid completion is allowed. Payments cannot exceed the current due amount. Refunds require an original payment, a reason, and an amount within its backend-provided remaining refundable cap and net paid funds. Cancellation preserves original totals/history, makes retained funds credit due, and never restores stock. Financial review precedes submission; ledger entries are not editable/deletable. Current-order reads refresh balances after verified success. The print view loads the saved snapshot, includes balance/credit, preserves list-return filters, and hides navigation/actions when printed.

Ingredients use grams, milliliters or whole pieces and optional thresholds. Stock history links to immutable receipts and earlier corrected movements. Reasoned opening/waste/correction entry reviews backend-provided before/change/after stock; no negative stock is allowed. A saved ingredient's stock is verified numerically, so `0` and `0.000` are the same quantity. Purchases use exact quantities and total ingredient cost, with explicit bag/bottle/box contents. Review shows original declarations, normalized quantities, comparable costs and stock effects. Two kg costing $24 adds 2000 g and displays $12/kg; unknown prices remain distinct from known zero. Backdated receipts and physical corrections do not overwrite the appropriate latest purchase basis. Low-stock dashboard warnings show current physical inventory independently of the order date, not planned demand. Dirty inventory entry is protected against dismissal/reload/history navigation, and unresolved inventory saves follow the same UUID reconciliation rules.

Menu & Recipes links every variant to its recipe page and marks a variant without one. A recipe states quantities for exactly one selling unit of that variant (one tray, piece, stick or package); each size has its own recipe and nothing is scaled between sizes. Ingredients are chosen from inventory, appear once, and use grams/kilograms, millilitres/litres or whole pieces to match their base unit. The estimate is the backend's calculation: selling price, estimated ingredient cost and ingredient contribution estimate are shown separately, with each ingredient's latest purchase date, receipt link, comparable unit cost and exact row amount. With the $12/kg example, 750 g contributes $9. A missing recipe or purchase price makes the estimate Incomplete with links to the affected records; unknown cost is never shown as zero, while a known zero cost is. The contribution is labelled an ingredient estimate, not net profit. Estimates are read again after a recipe save and on each visit, so recipe, selling-price and purchase changes appear. A recipe written for an earlier selling format is flagged until it is saved for the current one. Recipe saves are version-guarded without operation UUIDs: a conflict shows the latest recipe for explicit review, and an unconfirmed save is resolved by rereading the saved recipe, never by resubmitting blindly. The menu list shows recipe presence only; estimate completeness is on the recipe page.

Planning shows, for a chosen range of business dates, what remains to cook and what that needs. The period is kept in the URL and defaults to the backend's business date. Demand comes from Confirmed, Preparing and Ready orders; Pending, Completed and Cancelled orders are left out. Each food row gives ordered, prepared and remaining quantities with links to the contributing orders. Each ingredient row gives physical stock, earlier commitments, this period's demand, the stock left after earlier commitments (shown negative when they already exceed stock), and the shortage for the period and through it. Demand for a variant without a recipe makes the plan Incomplete, with links to the recipe page and the affected orders, and the quantities are then a lower bound. The frontend checks the backend's numbers against the agreed formulas and rejects a plan that double-counts commitments or hides a shortage. Planning never reserves or changes stock. The dashboard summarises preparation for its date and links to Planning and the shopping list. The shopping list for the same period shows only ingredients that stock cannot cover through that period, with what to buy, physical stock, earlier commitments and this period's demand; it is the backend's list, checked but not recalculated. Printing it hides navigation and actions, keeps the incomplete warning, repeats the table header on each page and does not split rows.

When preparation recording is enabled, Planning offers Record preparation while something remains. Staff enter how much of each remaining order line was prepared and what was actually used; a recipe estimate is never recorded in its place, and a preparation that used no tracked ingredient needs a note. Review shows prepared counts and physical stock before and after, the recipe version on record and the estimated ingredient cost, shown as unknown when an ingredient has no purchase. Nothing is deducted until the reviewed preparation is recorded, once, under an operation key. An unconfirmed save locks the entry until its status is checked; only the identical request can be retried, and only when no operation was recorded. The saved record at `/preparations/{id}` links to its orders and stock movements. Orders show prepared and remaining quantities, can be marked ready without attestation once every line is prepared, keep prepared lines when edited, and list what was prepared when cancelled; consumed stock is never returned automatically. Returned, wasted or miscounted ingredients are recorded from the preparation record as a stock movement linked to it. A wrong prepared count is corrected from the record in a reviewed form: a reason, signed changes to prepared counts and signed stock changes, applied together once. A count cannot be lowered while its order is Ready or Completed, and a lowered count returns to what remains to prepare unless the order is cancelled. The original record is never changed; its corrections are listed beside it.

## Verification

```powershell
npm test
npm run typecheck
npm run build
npm exec -- playwright install chromium
npm run test:e2e
npm run test:conformance
```

`npm run test:conformance` runs the fixture contract tests against the real [backend](../backend/README.md) instead of the in-memory fixtures. It needs the backend set up with `uv sync` and starts and stops a test-only server on port 8010 by itself; set `CONFORMANCE_URL` to use one that is already running. Each test gets a new database seeded like the fixture. Five tests that build fixture internals directly are skipped there, and one extra scenario, `tests/conformance/responses.live.ts`, puts every answer of a working day through the screens' own response checks. The differences found and how they were settled are in the [backend Phase B8 record](../backend/docs/phase-8/VERIFICATION.md#the-conformance-run).

`npm run test:watch` runs the behavioral tests interactively. Playwright starts/stops its own live-mode Vite server on port 4173; that port must be free. It intercepts API requests with deterministic development responses. Screenshots, a print PDF and failure traces are generated in ignored `test-results/`. The 73 browser checks cover the foundation, menu, reservations, snapshots, dashboard, filters/scroll return, fulfillment, financial review/credit/refunds, ingredients/purchases/stock links, recipes/estimates, planning, preparation recording and corrections, expiry/recovery, protected printing, focus/discard/history protection, 320/375/768/1280-pixel layouts, long text and 200% text zoom. The full Vitest suite contains 382 passing tests across 33 files.

Build output is `dist/`. `npm run preview` serves the built application but does not supply a backend; use a same-origin API reverse proxy for live integration. The [Phase 1](docs/phase-1/VERIFICATION.md), [Phase 2](docs/phase-2/VERIFICATION.md), [Phase 3](docs/phase-3/VERIFICATION.md), [Phase 4](docs/phase-4/VERIFICATION.md), [Phase 5](docs/phase-5/VERIFICATION.md), [Phase 6](docs/phase-6/VERIFICATION.md), and [Phase 7](docs/phase-7/VERIFICATION.md) records contain observed red/green results and outstanding live checks; Phases 1-5 each have a section for the 2026-10-10 review fixes summarised in [the implementation plan](FRONTEND_IMPLEMENTATION_PLAN.md#post-delivery-review-fixes).

## WebStorm

1. Open this frontend directory and choose the installed Node.js interpreter under Settings > Languages & Frameworks > JavaScript Runtime.
2. Open `package.json`, run `npm ci`, then use the run icon beside `dev:fixtures` for the local fixture workspace or `dev` for FastAPI integration.
3. Create npm run configurations for `test`, `typecheck`, `build`, and `test:e2e`. Use the project directory as the working directory. Install Chromium once before browser tests.
4. Set JavaScript/TypeScript breakpoints and attach a JavaScript Debug configuration to the local Vite URL. PyCharm can run the separately implemented FastAPI backend on port 8000.

Business/staff/menu confirmations and backend agreement remain tracked in [the implementation plan](FRONTEND_IMPLEMENTATION_PLAN.md). Development tests do not prove live authentication or authorize real business data.
