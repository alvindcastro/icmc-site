# Frontend / FastAPI Contract v1

Status: documented proposal, pending backend agreement and implementation. Base path: `/api/v1`. This contract supports the [decision register](DECISIONS.md) and [acceptance scenarios](ACCEPTANCE.md). Example IDs, users, currency, prices, and dates are development fixtures.

## Shared Representations

All requests/responses use JSON except an empty 204. Unknown request properties are rejected. IDs are opaque strings; the frontend does not parse them. `operation_id` is a client-generated UUID. Mutable records have an integer `version` starting at 1. Optional fields are listed explicitly; all other listed request fields are required. The backend returns authoritative computed values and never accepts client totals, balances, normalized costs, or stock on hand as facts.

| Type | Wire representation | Rules |
|---|---|---|
| Money | Integer `*_minor`, e.g. `21500` | One configured currency; safe JSON integer, absolute value <= 9007199254740991; backend additionally rejects any calculation that exceeds this bound |
| Currency | ISO code plus `minor_digits`, e.g. `USD`, `2` | Supplied by settings; do not hardcode cents or dollar symbols |
| Selling quantity | Positive integer, e.g. `2` | Counts trays/pieces/sticks/packages; max safe integer and backend-calculated amount bounds apply |
| Ingredient quantity | Exact decimal string, e.g. `"2000.000"` | Up to 3 decimal places for g/ml; pieces are integral; no exponent, negative zero, NaN, or Infinity |
| Normalized unit cost | Decimal string, e.g. `"0.012000000"` | Major currency per base unit, 9 decimal places; null if unknown, never silently zero |
| Calendar date | `YYYY-MM-DD` | Purchase/payment dates and filters are dates in the business calendar, not midnight UTC |
| Instant | RFC 3339 UTC, e.g. `2026-10-10T19:00:00Z` | Audit timestamps generated by backend |
| Local fulfillment | Date, `HH:mm`, IANA timezone, optional UTC offset | Backend resolves and validates; response includes the UTC instant and offset |
| Unit | `g`, `kg`, `ml`, `l`, `piece`, `bag`, `bottle`, `box` | Only explicit compatible conversions; packaging requires declared contents |

Backend decimal arithmetic retains exact conversion ratios and an unrounded purchase cost basis. Round each recipe's total estimated cost to minor units once, using half-up. Display normalized costs to 9 decimals; do not use that display-rounded value as the authoritative recipe cost basis. Overflow or unsupported precision is a 422 field error. Zero prices/costs are allowed only when explicitly entered; unknown values are null with an incomplete reason.

### Dates and Times

Fulfillment input is `{method, local_date, local_time, timezone, utc_offset, address}`. `method` is `pickup|delivery`; `timezone` must equal the settings timezone. `utc_offset` is optional/null for an unambiguous local time; for an ambiguous time, backend validation returns possible offsets, and staff choose one. Reject nonexistent daylight-saving times. Backend returns those local fields plus `fulfillment_at` (UTC); filters and dashboard group by the business local date. The browser's timezone cannot change the business time.

`address` is required/nonblank for delivery and null for pickup. Contact phone is a trimmed string, not a number. Quote validation returns a pickup location from confirmed settings; order snapshots preserve that location and the original business timezone. A timezone/currency change is an operator migration decision, not an editable frontend preference.

### Lists and Query State

List endpoints accept `page` (default 1, minimum 1) and `limit` (default 25, maximum 100). Response is `{items, page, limit, total, has_next}`; `total` counts matches. Default ordering is documented below, with ID as the final tie-breaker. No matches returns 200 and `items: []`, including an out-of-range page. Filter changes reset page to 1. The frontend preserves filters/sort/page in the URL and scroll position in memory on detail return. Each list request is a fresh snapshot, not a transaction spanning pages.

`q` is a trimmed, case-insensitive substring search (maximum 200 characters). `date_from`/`date_to` are inclusive local business dates, validated so from <= to. Status filters may contain comma-separated allowed enum values. Unknown query values produce 422, not an silently ignored filter.

### Errors and Permitted Actions

Errors use `{error: {code, message, request_id, field_errors, details}}`. `field_errors` is always an array of `{path, code, message}` using JSON Pointers against the request body, e.g. `/draft/items/0/quantity`. Query pointers use `/query/page`. Global failures have an empty array. Backend messages describe recoverable errors and omit credentials/tracebacks. FastAPI default validation errors must be adapted to this envelope.

| HTTP | Codes / behavior |
|---|---|
| 400 | `invalid_json`, invalid protocol input |
| 401 | `unauthenticated`, `session_expired`, or `invalid_credentials`; expiry is distinct from invalid login credentials |
| 403 | `action_forbidden`, `csrf_invalid`; authorization always enforced server-side |
| 404 | `not_found`, including unknown operation IDs |
| 409 | `version_conflict`, `operation_payload_mismatch`, `operation_in_progress`, `quote_stale`, `action_not_allowed`, `settings_unconfirmed`, `menu_unconfirmed`, `insufficient_stock` |
| 422 | `validation_failed`, including amount bounds, bad quantities, unit mismatch, invalid DST time |
| 429 | `rate_limited`, with `Retry-After` |
| 500/503 | `internal_error`/`temporarily_unavailable`; mutations have an uncertain outcome until reconciled |

Resource responses include `permitted_actions`, an object whose named entries are `{allowed: boolean, reason_code: string|null, reason: string|null}`. Orders always include `edit`, `confirm`, `start_preparing`, `mark_ready`, `complete`, `cancel`, `record_payment`, `refund`, and `record_preparation`. A blocked action has a reason. Settings `capabilities` control navigation/workflow availability; a resource action controls the actual mutation. Both are backend decisions. Recheck permissions when saving, even if a button was previously enabled.

Example validation response:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Check the highlighted fields.",
    "request_id": "request_example",
    "field_errors": [
      {"path": "/draft/items/0/quantity", "code": "positive_integer_required", "message": "Enter a whole package quantity greater than zero."}
    ],
    "details": {}
  }
}
```

## Auth and Settings (Phase 1)

Deployment baseline: same-origin frontend/API through a development proxy or deployment reverse proxy. Requests include cookies. Production cookie is an opaque session ID with `HttpOnly`, `Secure`, `SameSite=Lax`, and `Path=/`; the server rotates it on sign-in, invalidates it on sign-out, and sends `Cache-Control: no-store` for protected/auth responses. A localhost HTTP development cookie is explicitly development-only. Require an approved Origin and CSRF token for mutations, including sign-in/sign-out; cookie flags do not replace those checks.

| Method / path | Request | Success |
|---|---|---|
| `GET /auth/csrf` | No body; available before sign-in | 200 `{csrf_token}` associated with a short-lived pre-auth or authenticated session; no protected data |
| `POST /auth/sign-in` | Interim `{username, token}`, `X-CSRF-Token` | 200 session response plus rotated cookie; generic invalid-credentials response on failure |
| `GET /auth/session` | Cookie | 200 session response; otherwise 401 |
| `POST /auth/sign-out` | Empty object, `X-CSRF-Token` | 204, server session invalidated and cookie cleared; an already-ended session is also 204 |
| `GET /settings` | Authenticated | 200 business settings below |

Session response: `{user: {id, username, display_name, role}, csrf_token, idle_expires_at, absolute_expires_at}`. Pilot role is `staff`. Limits are 30 idle minutes and 12 absolute hours, enforced by backend; successful authenticated business requests renew idle expiry, but session polling alone does not. `GET /auth/session` reports the current expiry. The sign-in response has a new authenticated CSRF token. Frontend refinement (2026-10-10): session, quote, and preview deadlines are compared against the server clock taken from each response's standard `Date` header, so a wrong device clock cannot end them early; responses must carry that header, and without it the device clock is used. The backend remains the authority on expiry.

Interim requirement, requested by the user on 2026-10-07: sign in as `admin` with a token rather than a password. Send the token exactly as entered, without trimming; reject blank/invalid tokens. Field errors reference `/token`. The login token is distinct from the session's CSRF token and is never retained in browser storage or used to bypass backend validation. Explicit development fixtures accept `admin` / `local-admin-token`; a live backend must validate its own configured secret. The account name `admin` uses the current staff permission set; separate administration permissions remain outside this pilot.

On 401, stop pending automatic retries, clear protected state, and navigate to sign-in with a validated relative return route. Never replay a prior mutation after login. Retain only non-sensitive unresolved operation IDs for subsequent authorized lookup. Sign-out clears browser data immediately; if the network result is uncertain, show server sign-out as unconfirmed and retry explicit sign-out until confirmed. Do not claim the remote session ended based on local cleanup alone.

Settings response: `{version, environment, confirmation, currency, minor_digits, timezone, fulfillment_methods, pickup_location, delivery_policy, tax_policy, payment_methods, capabilities}`. `environment` is `development|live`. `confirmation` contains booleans `currency`, `timezone`, `fulfillment`, `delivery`, `tax`, and a `confirmed_at` nullable timestamp. Production financial mutations require all relevant confirmations.

`delivery_policy = {mode: "manual_amount"|"fixed_amount"|"disabled", fixed_charge_minor: integer|null}`. Proposed `tax_policy = {mode: "manual_amount", inclusive: false}`; B05 may change it before live agreement. `payment_methods` is the permitted enum subset of `cash`, `bank_transfer`, `other`. `capabilities` has booleans `orders`, `menu`, `payments`, `inventory`, `purchases`, `recipes`, `planning`, `preparation_recording`. The backend enables only released workflows. Unconfirmed development settings must be visibly labeled provisional; live endpoints fail closed rather than use fixture defaults.

Backend refinement (2026-10-10), from implementing this section in backend Phase B1. None of it changes a request or response shape.

- Idle renewal: a business request that passes authentication renews idle expiry whatever its own outcome, including a refused save. Requests under `/auth` never renew it.
- `GET /settings` returns 503 `temporarily_unavailable` until an operator has created the settings record; no defaults are served. `capabilities` reports a workflow as on only when it is enabled and implemented by the running backend.
- `csrf_invalid` (403) is returned for a missing or wrong token, a token whose pre-auth session has ended (they last 15 minutes), an unapproved `Origin`, and a mutation with no `Origin` header. The frontend forgets a refused token and fetches a new one on the next explicit attempt; it never resends on its own. A mutation on an expired session that carries that session's own token is 401 `session_expired`, not 403.
- Sign-out returns 204 for a session that is already ended or expired, provided the CSRF token is that session's.
- Sign-in is locked with 429 `rate_limited` and `Retry-After` (seconds) after five failures in 15 minutes, counted for the whole backend; while locked, the right token is refused too.
- The session cookie is `food_session`, with no lifetime of its own. It is always `Secure` when `environment` is `live`.
- Every response carries `X-Request-ID`, equal to `error.request_id` on failures. An unknown query parameter is 422 at `/query/<name>` on every route. Instants are given to the whole second. Field errors use `required` for a missing or blank value and `unknown_field` for a property or query parameter the route does not define.

If a separate development API origin is needed, allow exact frontend origins, credentials, and headers `Content-Type`, `X-CSRF-Token`, `Idempotency-Key`, and expose the `Date` response header (`Access-Control-Expose-Headers: Date`); no wildcard credentialed origin. This follows the [FastAPI CORS documentation](https://fastapi.tiangolo.com/tutorial/cors/). Cookie behavior follows [MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie).

## Versions and Conflict Handling

Every existing-order mutation, including status/payment/refund/preparation, requires body `expected_version`. Compare and update atomically in the same backend transaction as all associated ledger/stock effects. Each successful mutation increments the order version once; read-only quotes do not. Menu, ingredient, and recipe updates also require their own `expected_version`. A purchase touching inventory or preparation consuming ingredients revalidates the relevant current stock in its transaction.

Stale input returns 409 `version_conflict` with `details: {resource_type, resource_id, expected_version, current_version, latest_resource}`. No partial mutation occurs. Preserve unsaved values, show latest values beside the draft, and require staff to resolve changes, request a new quote, and review again. Never replace the expected version automatically and resubmit. A missing version returns a 422 field error. This contract uses an explicit JSON version precondition rather than the HTTP `If-Match` mechanism; [MDN documents the analogous lost-update problem](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/If-Match).

## Operation IDs and Uncertain Results

Require `Idempotency-Key: <operation_id>` for menu food/variant creation and updates, ingredient creation and updates, order creation and all persisted order mutations, payments, refunds, purchases, stock movements, preparation, and preparation corrections. Quote/preview requests have no side effects and do not require a key. Generate a key once for a reviewed submission and retain it through network retries. A request changing the body, target, or expected version is a new attempt with a new key, only after the previous attempt is conclusively resolved.

Backend operation storage is durable and scoped to the business. Bind each key to its method, path, and canonical JSON body (including expected version and quote/preview ID); auth cookies/CSRF tokens are not part of this fingerprint. Authorize lookups/replays as well as new mutations. Record business effects and the terminal success response atomically. Persist terminal validation/conflict rejections so a delayed request for that same key cannot become a later success. Rollback yields no partial ledger, order, or movement.

An identical completed request returns its recorded HTTP status/body, with `Idempotency-Replayed: true`, before rechecking now-stale versions or expired quotes. A different fingerprint is 409 `operation_payload_mismatch`. An in-flight identical request is 409 `operation_in_progress`, with `Retry-After`. There is no blind client retry of a timed-out mutation.

`GET /operations/{operation_id}` returns 200 `{operation_id, state, resource_type, resource_id, result, error, started_at, completed_at}`. `state` is `processing|succeeded|rejected`; success `result` is `{http_status, body}` and rejection `error` is the original error envelope plus HTTP status. Fields irrelevant to a state are null. A rejected operation guarantees no business side effect. Unknown ID returns 404; it does not prove a delayed original request cannot still arrive.

| Lookup outcome | Frontend behavior |
|---|---|
| Succeeded | Show confirmed result, then refresh current resource (recorded response may have an older version) |
| Rejected | Preserve input, display rejection; a corrected/new reviewed attempt gets a new key |
| Processing | Keep submission blocked; poll read-only lookup with bounded backoff up to 30 seconds, then offer explicit Check status |
| 404 | Retain the original key and exact request; offer explicit retry of that same attempt, never a replacement key based only on absence |
| 401 | Sign in, then look up the ID before staff explicitly resume; no automatic mutation |
| Network/5xx | Keep result uncertain; offer Check status; do not claim failure or enable a new key |

If expiry has cleared the protected draft and lookup is 404, stop and require backend/operator reconciliation of that key before accepting a replacement. Backend recovery must determine whether an admitted `processing` request committed and durably close it; a client timeout is not sufficient evidence of rejection. Retain operation IDs/fingerprints/results for at least the associated business record's lifetime, including archive/backup; no short deduplication expiry.

Backend refinement (2026-10-10), from implementing this section in backend Phase B2. None of it changes a request or response shape.

- An operation key must be a UUID in its usual hyphenated form; letter case is ignored. A missing or malformed key is 422 at `/header/Idempotency-Key`.
- What is recorded under a key is every outcome of the change itself: success, and any 4xx it produces, including validation, conflict and a missing record. A refusal before the change is attempted is not recorded and leaves the key unknown: an ended session, a CSRF or capability refusal, malformed JSON, a body that is not a JSON object.
- The record, the change and the stored answer commit together, so `processing` is not normally observable: an identical request sent while the first is running waits and then receives the replay. `operation_in_progress` remains possible in principle.
- A write that cannot start within the backend's busy timeout is 503 `temporarily_unavailable` with `Retry-After`; nothing is recorded, so a status check answers 404.
- An operator can close a key the backend never saw. The lookup then answers `rejected` with HTTP status 409 and code `operation_closed`, and the message carries the operator's reason. The original request is refused if it arrives later.
- A rejected operation has null `resource_type` and `resource_id`. Operation lookups need a signed-in session and no particular capability.

Frontend refinement (2026-10-10), no backend change: closing an editor whose save is still unresolved requires confirmation, and the exact request (key, method, path, body) is retained in protected memory, never in browser storage. The page-level status check can therefore still offer the identical-key/body retry after a 404 once the editor is closed. A reload or the end of the session clears that request; the previous paragraph then applies.

## Menu (Phase 2)

Food response: `{id, version, name, category_id, description, available, confirmation_status, variants, permitted_actions}`. Variant: `{id, version, food_id, label, selling_unit, price_minor, available, confirmation_status, package_contents, recipe_id, permitted_actions}`. `selling_unit = tray|piece|stick|package`; `package_contents = {quantity: positive_integer, unit: "piece"}` for packages, otherwise null. `confirmation_status = provisional|confirmed`; staff availability cannot bypass missing confirmation in live mode. `recipe_id` is null until Phase 6.

Phase 2 implementation refinements, still pending backend agreement: food actions are `edit` and `add_variant`; variant actions contain `edit`, using the shared permitted-action representation. Settings capability `menu` enables food creation/list access; all mutations are authorized again by the backend. Food names and variant labels are trimmed, nonblank, and at most 200 characters; descriptions are at most 2000 characters, with an empty string in responses when absent. Category IDs must reference existing categories. Prices are nonnegative safe integer minor units, including explicitly entered zero. Package contents require a positive safe integer whole-piece count. Query `available` filters foods, not nested variants; unavailable variants remain in food responses for staff editing.

All four menu mutations below require operation keys and support the shared operation lookup/replay protocol. Successful food edits increment the food version; adding/editing a nested variant also advances its parent food aggregate version, while variant edits advance that variant's own version. Both changes occur atomically. A nested variant response is followed by a fresh food list/detail read, never a client-manufactured food version. Conflict details include the complete latest food or variant and its permitted actions. Staff must explicitly review that record before retaining their draft against its version; no automatic overwrite/retry is permitted.

Phase 2 menu recovery uses explicit read-only Check save status/Check previous save actions while an operation is processing or uncertain. Submission remains blocked throughout; no automatic polling or mutation replay occurs. The exact in-memory request/key can be explicitly retried after a 404, from the open editor or from the menu page once the editor has been closed. After that request is lost to a reload or the end of the session, unknown status requires backend/operator reconciliation. This is a menu-specific frontend exception to the bounded automatic lookup polling described in the shared operation table.

| Method / path | Request / filters | Success |
|---|---|---|
| `GET /categories` | Pagination | Category list `{id, name}`, name ascending |
| `GET /foods` | `q`, `category_id`, `available` plus pagination | Food list, name ascending; unavailable records retained |
| `GET /foods/{id}` | None | 200 Food |
| `POST /foods` | `{name, category_id, description?, available}`, operation key | 201 Food; confirmation defaults to provisional |
| `PATCH /foods/{id}` | `{expected_version}` plus changed editable fields, operation key | 200 Food; no hard delete |
| `POST /foods/{id}/variants` | `{label, selling_unit, price_minor, available, package_contents}`, operation key | 201 Variant |
| `PATCH /variants/{id}` | `{expected_version}` plus changed variant fields, operation key | 200 Variant; sellable-unit/package identity immutable once used on an order |

Backend refinement (2026-10-10), from implementing this section in backend Phase B2. None of it changes a request or response shape.

- Every menu route, reading included, is 403 `action_forbidden` unless the `menu` capability is enabled.
- A PATCH changes only the fields it sends. An explicit null for a field that cannot be empty is a field error, and an edit that changes nothing still advances the version. Checks run in this order: the shape of the body, a missing record (404), rules that depend on the record, then the version (409).
- The package rule is judged on the variant as it would be after the edit: a missing piece count is reported at `/package_contents/quantity`, and contents on a unit that is not a package at `/package_contents`. A change of unit or contents after use on an order is reported at `/selling_unit` or `/package_contents/quantity` with code `immutable_after_order`. An unknown category is `unknown_category`, at `/category_id` or `/query/category_id`.
- `available` in the query accepts only `true` or `false`. Search and name ordering ignore letter case; `%` and `_` in search text are literal.
- Confirmation is recorded against the version the operator reviewed and advances that version (and the food's, for a variant). Only a change to a material value withdraws it: a food's name, or a variant's label, unit, package contents or price.
- Categories are unique by name without regard to letter case and are added by the operator.

Confirmation is an audited backend/operator step after B06-B08 review, outside the pilot editor. A confirmed variant's material name/unit/package/price changes reset its confirmation until revalidated; already-saved order snapshots do not change. Unavailable food hides its variants from new selection even if a variant itself is available. Existing unavailable lines remain readable and may retain/decrease quantity or change notes; adding/increasing/swapping requires a currently available and confirmed variant in live mode.

## Orders and Quotes (Phase 3)

Phase 3 implementation refinements below remain proposals pending FastAPI agreement. `capabilities.orders` enables Orders/Dashboard, and live reservations fail closed until currency, timezone, fulfillment, delivery, and tax are confirmed. Only available, confirmed foods/variants may be newly sold in live mode; explicit development examples remain provisional.

Order draft: `{customer: {name, phone, notes?}, fulfillment, items, notes?, delivery_charge_minor, tax_minor}`. `items` is a nonempty array of `{client_line_id, order_item_id?, variant_id, quantity, preparation_notes?}`. `client_line_id` is a unique draft string used to match quote/error rows. Omitted existing line IDs mean removal. Existing `order_item_id` must belong to this order and retains its identity, names, unit, package contents, and price; swapping a variant is remove/add and allowed only when unprepared. The client cannot send a replacement snapshot price.

| Method / path | Request / query | Success |
|---|---|---|
| `GET /orders` | `q` customer/reference, local `date_from/date_to`, `status`, `sort=fulfillment_asc|fulfillment_desc`, pagination | Order summaries; default fulfillment ascending then ID |
| `GET /orders/{id}` | None | 200 full Order |
| `GET /dashboard` | `date` optional, default backend business today | 200 `{business_date, timezone, today, upcoming}`; paginated summary collections, default first 25; use Orders for additional rows |
| `POST /orders/quote` | `{order_id?, expected_version?, draft}`; both optional fields required together for an edit | 200 Quote |
| `POST /orders` | `{quote_id, draft, initial_status: "pending"|"confirmed", acknowledge_credit: boolean}`, operation key | 201 Order; confirmed creation writes Pending then Confirmed audit events atomically |
| `PUT /orders/{id}` | `{expected_version, quote_id, draft, acknowledge_credit: boolean}`, operation key | 200 updated Order; no preparation-status change |

Quote: `{id, expires_at, order_id, expected_version, settings_version, currency, minor_digits, fulfillment, lines, subtotal_minor, delivery_charge_minor, tax_minor, total_minor, settlement_total_minor, net_paid_minor, balance_due_minor, customer_credit_minor, credit_acknowledgment_required}`. Each line contains `client_line_id`, nullable `order_item_id`, `variant_id`, `quantity`, snapshot name/label/unit/package/price fields, `line_total_minor`, and nullable prepared/remaining quantities. New-order net paid is zero.

Quotes last five minutes and bind to the validated draft, current settings, existing order version, and new-line menu versions. Save must match the quoted draft exactly. Save rechecks versions, new-line price/availability/confirmation, relevant settings, and expiry atomically; changed dependencies return 409 `quote_stale` or `version_conflict` with no save. Refresh/review the quote; do not silently update displayed prices. Existing agreed prices remain unchanged on quantity/notes edits. Invalid manual delivery/tax input is a field error; pickup charge is always zero; fixed delivery charge is supplied by backend. When `delivery_policy.mode` is `disabled` the frontend offers no delivery method; a saved delivery order must be changed to an enabled method before it can be quoted again, reported at `/draft/fulfillment/method`. Quotes failing or becoming stale cannot appear as current totals.

With provisional USD examples, the returned subtotal/total is 21500, not a client calculation used as authority. A later menu price/name change does not affect this saved order.

Full Order: `{id, reference, version, currency, minor_digits, customer, fulfillment, items, notes, status, preparation_tracking, cancellation_requires_stock_acknowledgment, subtotal_minor, delivery_charge_minor, tax_minor, total_minor, settlement_total_minor, payments_minor, refunds_minor, net_paid_minor, balance_due_minor, customer_credit_minor, payment_status, ledger, status_history, permitted_actions, created_at, updated_at}`. `preparation_tracking = manual|recorded` follows the capability/migration rule in the register. Each item has stable `id`, `variant_id`, immutable snapshot fields, quantity, line total, notes, prepared/remaining quantities; the latter are null in manual mode. Ledger/history records include actor ID/display-name snapshot and audit timestamp. The Phase 4 refinement `cancellation_requires_stock_acknowledgment` is a required backend-derived boolean: false in the manual pilot, true when cancellation retains recorded consumption requiring explicit acknowledgment. Do not infer this from preparation counts in the client.

Snapshot wire fields are `food_name`, `variant_label`, `selling_unit`, nullable `package_contents`, `unit_price_minor`, `quantity`, `line_total_minor`, `preparation_notes`, `prepared_quantity`, and `remaining_quantity`. Quote lines add `client_line_id` and nullable `order_item_id`; saved lines instead have stable `id`. History is `{id, from_status: status|null, to_status, changed_at, actor: {id, display_name}, reason: string|null}`; initial Pending has null previous status. Cancellation requires the saved nonblank reason; other events may omit reason or return null. Fulfillment returns the input local fields plus resolved `fulfillment_at`, selected `utc_offset`, and nullable `pickup_location`. All amounts are nonnegative safe integer minor units; customer/credit/balance/payment values are authoritative. Zero settlement with zero net paid is Paid, not Unpaid.

Customer name/contact are trimmed, nonblank, and limited to 200/50 characters. Customer/order notes allow 2000 characters; delivery addresses and preparation notes allow 1000. Omitted notes return empty strings, not missing/null fields. Unknown request fields and client-supplied snapshot prices are rejected. DST ambiguity returns a field error at `/draft/fulfillment/utc_offset` and `details.utc_offsets` with the permitted occurrences; selecting an offset does not replace backend resolution. Query search includes customer name, contact phone, and reference; comma-separated status filters support active/not-cancelled dashboard links.

Pending confirmation is included in Phase 3 through `POST /orders/{id}/transitions` with `{expected_version, to_status: "confirmed"}` and an operation key, following a separate review of the saved order. It does not edit fields or take payments. Later transitions, cancellation, payment/refund entry, and printing remain Phase 4. Phase 3 operation recovery follows bounded read-only polling in the shared protocol; successful lookup triggers a fresh current Order read, and no prior mutation is replayed after sign-in.

Summary: `{id, reference, version, customer_name, customer_phone, fulfillment_at, fulfillment_local_date, fulfillment_local_time, fulfillment_timezone, fulfillment_method, status, payment_status, currency, minor_digits, total_minor, balance_due_minor, customer_credit_minor}`. Dashboard uses the same summaries; `upcoming` excludes today's rows and Cancelled/Completed orders. `today` excludes Cancelled but includes Completed orders for daily review. Filtering/sorting is backend business-time behavior.

## Status and Payments (Phase 4)

Status enum: `pending`, `confirmed`, `preparing`, `ready`, `completed`, `cancelled`. Normal transitions move one step forward. No arbitrary jumps/reversals. Cancellation is separate, permitted from Pending/Confirmed/Preparing/Ready, requires a reason, and keeps the original totals/ledger/consumption. Backend returns explanatory unavailable actions for all other transitions.

| Method / path | Request | Success |
|---|---|---|
| `POST /orders/{id}/transitions` | `{expected_version, to_status}` plus operation key | 200 Order with dated history and new permissions |
| `POST /orders/{id}/cancel` | `{expected_version, reason, acknowledge_consumed_stock: boolean}` plus operation key | 200 Order; true acknowledgment required when recorded consumption exists |
| `POST /orders/{id}/payments` | `{expected_version, amount_minor, paid_on, method, reference?, note?}` plus operation key | 201 `{entry, order}` |
| `POST /orders/{id}/refunds` | `{expected_version, payment_id, amount_minor, refunded_on, method, reason, reference?, note?}` plus operation key | 201 `{entry, order}` |

Ledger entry: `{id, type: "payment"|"refund", payment_id, amount_minor, refundable_minor, business_date, method, reference, note, reason, operation_id, recorded_at, recorded_by: {id, display_name}}`. Original payments have null `payment_id` and reason; refunds reference an original payment and require a reason. Phase 4 adds required `refundable_minor`: the backend-derived remaining original-payment amount after its refunds, or null for refund entries. This derived read field changes as refunds are appended; original payment amount/date/method/reference/note/audit fields remain immutable. Do not edit/delete ledger entries. The UI consumes this cap and current balance/net paid amounts rather than inventing refund eligibility. Errors for exceeding a balance or refundable amount attach to `/amount_minor` and include `details.maximum_amount_minor`. Revalidate the version and amount atomically; two simultaneous payments cannot overpay. A quoted edit must recheck its version at commit so a payment arriving during calculation cannot be overwritten. Use the [financial policy](DECISIONS.md) for settlement/credit, including cancellation.

Financial amounts are positive safe integers. Dates are valid `YYYY-MM-DD` business dates, not browser-local instants; the default comes from `GET /dashboard.business_date` and remains editable. Methods must be enabled in `settings.payment_methods` (`cash|bank_transfer|other`). References allow 200 characters, notes 2000; omitted values return empty strings. Cancellation/refund reasons are trimmed, nonblank, and limited to 1000 characters. Unknown fields are rejected. No additional past/future-date restriction is selected by this proposal.

Financial success is the complete `{entry, order}` result, not a raw Order. The entry must be present in that Order's ledger and carry the submitted operation UUID. The shared operation envelope uses `resource_type: "order"`, `resource_id: order.id`, and the exact original wrapped result in `result.body`; transition/cancellation results remain raw Orders. Successful mutations increment the expected order version once. Replay returns the immutable original response before stale-version checks; both direct success and verified lookup trigger a fresh current-order read. Only the UUID is persisted in the existing order-operation marker, never a financial draft. A missing operation permits an explicit identical-body/key retry only while that attempt survives in memory; after expiry/reload, operator reconciliation is required if its status remains unknown.

When `preparation_recording=false`, Ready/Completed uses staff attestation and causes no stock change. The frontend attestation checkbox gates confirmation; the transition body remains `{expected_version, to_status}`. When enabled, both require zero remaining quantity on every line and backend permissions remain authoritative. Payment settlement is not a requirement for completion. The protected `/orders/{id}/print` frontend route reads the authoritative matching Order snapshot and current balance/credit, not the current menu; printing adds no backend mutation. These refinements are implemented only in explicit development fixtures until the backend maintainer accepts and implements them.

## Inventory and Purchases (Phase 5)

Ingredient: `{id, version, name, base_unit: "g"|"ml"|"piece", low_stock_threshold, stock_on_hand, low_stock, latest_unit_cost, latest_purchase_date, permitted_actions}`. Base unit is immutable once used. `low_stock_threshold` is an optional decimal-string quantity; `low_stock` is true when known threshold and stock <= threshold. Physical stock cannot become negative; review/register a real correction before saving a consumption/waste that exceeds stock.

Phase 5 frontend refinements, proposed for backend agreement: `permitted_actions` explicitly contains `edit`, `opening`, `waste`, and `correction`, using the shared allowed/denied reason schema. New ingredients have version 1, zero stock, and both latest cost/date null. The frontend verifies a saved ingredient's stock numerically, so `"0"` and `"0.000"` are the same quantity; within one movement result the ingredient's `stock_on_hand` and the movement's `after_quantity` must still be the identical string. A successful metadata edit increments the version once without changing stock or purchase history; this pilot's PATCH does not change base units. Clearing an optional threshold sends null. Ingredients require `inventory`; purchases require both `inventory` and `purchases`. Live inventory access requires confirmed business currency and timezone, independently of order fulfillment/tax settings. Ingredient names and supplier names are 1-200 characters; reasons/notes are up to 2000 characters; purchases contain 1-100 rows.

Movement: `{id, ingredient_id, delta_base_quantity, before_quantity, after_quantity, type, reason, purchase_id, preparation_id, corrects_movement_id, operation_id, recorded_at, recorded_by}`. `type = opening|purchase|consumption|waste|correction`; linkage fields are nullable. Opening, waste, and correction require a reason and a nonzero delta; a correction changes the ledger with a new movement, not editing old entries. Opening is allowed once per ingredient, before other movements, with a positive delta. Waste has a negative delta. A correction can be signed but must leave stock nonnegative. Related corrections must reference an existing movement of the same ingredient. A movement save increments the ingredient version once. `recorded_by` is a server-assigned staff display-name snapshot; the backend also retains authenticated staff identity in its audit storage, never accepting attribution from the draft. Preparation links are display-only identifiers until Phase 7 provides that workflow; Phase 5 rejects a new preparation link while recording is disabled.

Purchase draft: `{purchased_on, supplier, note?, items: [{client_line_id, ingredient_id, quantity, unit, pack_contents, total_cost_minor}]}`. `quantity` is a positive decimal string; pack count is integral when using bag/bottle/box. `pack_contents = {quantity, unit}` for packaging, with a supported physical unit; otherwise null. Purchase lines cannot combine currencies, dimensions, or unknown pack sizes. Duplicate ingredient lines may remain distinct receipt lines and are aggregated only for the resulting stock validation.

| Method / path | Request / filters | Success |
|---|---|---|
| `GET /ingredients` | `q`, `low_stock`, pagination | Ingredient list, name ascending |
| `GET /ingredients/{id}` | None | 200 Ingredient |
| `POST /ingredients` | `{name, base_unit, low_stock_threshold?}` | 201 Ingredient with zero stock and null cost |
| `PATCH /ingredients/{id}` | `{expected_version, name?, low_stock_threshold?}` | 200 Ingredient |
| `GET /ingredients/{id}/movements` | Pagination | Movement list, recorded_at descending then ID |
| `POST /ingredients/{id}/movement-preview` | `{expected_version, type: "opening"|"waste"|"correction", delta_base_quantity, reason, preparation_id?, corrects_movement_id?}` | 200 `{id, expires_at, ingredient_id, expected_version, before_quantity, delta_base_quantity, after_quantity}` |
| `POST /ingredients/{id}/movements` | Same reviewed input plus `preview_id`, operation key | 201 `{movement, ingredient}` |
| `GET /purchases` | `q` supplier/reference, `supplier`, `date_from/date_to`, pagination | Purchase summaries, purchased_on descending then ID |
| `GET /purchases/{id}` | None | 200 immutable receipt |
| `POST /purchases/preview` | `{draft}` | 200 `{id, expires_at, currency, minor_digits, items, total_cost_minor}` |
| `POST /purchases` | `{preview_id, draft}`, operation key | 201 `{purchase, ingredients}` with confirmed stock and price updates |
| `GET /ingredients/{id}/prices` | Pagination | Price history, purchased_on descending, recorded_at descending, ID |

Preview rows include `client_line_id`, `ingredient_id`, `base_quantity`, `base_unit`, `total_cost_minor`, `unit_cost`, `ingredient_version`, `before_quantity`, and `after_quantity`. Rows retain draft order and identifiers. Repeated ingredient rows show sequential before/after stock effects; the saved ingredient version increments once per receipt, not once per row. Preview lasts five minutes and binds the exact input and relevant ingredient definitions/versions; save revalidates them atomically or returns `quote_stale`/`version_conflict`. Concurrent additive purchases may conservatively require a new preview; replay of an already-committed purchase still returns its stored success. Movement previews have the same TTL/binding behavior. All receipt rows, movements, price history, stock updates, and the terminal operation result commit atomically, with no partial effects on rejection.

Purchase summary: `{id, reference, purchased_on, supplier, currency, minor_digits, total_cost_minor, recorded_at}`. The list does not require full receipt items.

Purchase receipt: `{id, reference, purchased_on, supplier, note, currency, minor_digits, total_cost_minor, items, operation_id, recorded_at, recorded_by}`. Immutable items are `{id, ingredient_id, ingredient_name, base_unit, quantity, unit, pack_contents, base_quantity, unit_cost, total_cost_minor, stock_movement_id}`. Original quantities/units/pack declarations retain the reviewed representation; receipt names/base units are snapshots. Price-history rows contain these item fields plus `{purchase_id, reference, supplier, purchased_on, recorded_at, currency, minor_digits}`. `recorded_by` has the same server-assigned display snapshot as movements. Latest cost basis is the maximum `(purchased_on, recorded_at, line_id)` so entering an older receipt does not replace a later business-date price. Unknown cost/date are both null; a known zero cost remains a dated purchase basis.

Operation successes use `resource_type: "ingredient"` for ingredient edits and movements, and `"purchase"` for receipts. Bodies are exactly the endpoint success shapes above; the result resource ID and movement/receipt operation ID must agree with the lookup. Replays retain their original snapshots; the frontend rereads current detail/history afterward. Dashboard low-stock warnings query `GET /ingredients?low_stock=true` separately from date-selected orders and link to the complete paginated ingredient list. These are current physical quantities, never planned demand. Receipt/correction stock links locate their movement through the existing paginated history endpoint, with bounded read-only lookup and recoverable failures.

Conversions: 1 kg = 1000 g; 1 l = 1000 ml; piece to piece only. Packaging multiplies pack count by declared contents before compatible normalization. No density, count-to-weight, or implicit bag-size conversion. Example: 2 kg, 2400 USD minor units -> 2000 g, `0.012000000` USD/g and 12 USD/kg. Purchases and corrections update stock, but only purchases update purchase price history. Any correction to a receipt's physical quantity uses a linked stock correction; editing receipts or repricing historical purchases is outside the pilot.

## Recipes and Cost Estimates (Phase 6)

Recipe: `{id, version, variant_id, yield: {quantity: 1, selling_unit, package_contents}, items: [{ingredient_id, quantity, unit}], recorded_at, updated_at}`. Yield is exactly one current sellable variant; a 100-piece package recipe describes all 100 pieces. Each tray size gets its own recipe; no inferred ratios. Ingredient rows are unique by ingredient ID, positive and compatible with its base dimension. Empty ingredient lists are not complete recipes.

| Method / path | Request | Success |
|---|---|---|
| `GET /variants/{id}/recipe` | None | 200 Recipe or 404 `not_found` |
| `PUT /variants/{id}/recipe` | `{expected_version, yield, items}`; null version required only when creating | 200 Recipe (existing) or 201 (new); conflict if creation raced |
| `GET /variants/{id}/estimate` | None | 200 Estimate, including incomplete estimates |

Estimate: `{variant_id, recipe_version, currency, selling_price_minor, ingredient_cost_minor, ingredient_contribution_minor, complete, missing, basis, calculated_at}`. Incomplete estimates have null aggregate cost/contribution, `complete: false`, and `missing: [{code: "recipe_missing"|"price_missing", ingredient_id, variant_id}]`. `basis` has ingredient ID, base quantity, purchase/line ID, purchase date, displayed unit cost, and per-row estimated amount. A known zero purchase cost remains a real basis, distinct from missing cost. Recompute estimates when recipes, selling prices, or applicable latest purchase costs change; label contribution as an ingredient estimate, not net profit.

Phase 6 frontend refinements, proposed for backend agreement. Recipes require the `menu`, `recipes`, and `inventory` capabilities; live use also requires confirmed business currency and timezone. Request rows stay `{ingredient_id, quantity, unit}`: `quantity` is a positive ingredient-quantity string and `unit` is one of that ingredient's physical units (`g|kg`, `ml|l`, or `piece`, whole counts only). A recipe has 1-100 rows; row order and the entered quantity/unit representation are retained. Response rows add the display fields `ingredient_name` and `base_unit`. `PUT` requires `yield` to equal the variant's current selling unit and package contents (422 at `/yield`) and reports an empty list at `/items`, an unknown or repeated ingredient at `/items/{i}/ingredient_id`, an incompatible unit at `/items/{i}/unit`, and an invalid quantity at `/items/{i}/quantity`; unknown fields are rejected. `expected_version` is null only while no recipe exists (otherwise 422 at `/expected_version`). A stale version, including a null version sent after another creation, returns 409 `version_conflict` with `resource_type: "recipe"` and the complete latest recipe. A successful save increments the recipe version once and sets the variant's `recipe_id` without advancing the variant version. The pilot has no recipe deletion. `GET /variants/{id}/recipe` returns 404 for an unknown variant and for a variant without a recipe; the frontend establishes the variant through `GET /foods/{id}`.

Recipe saves carry no operation key: a version-guarded `PUT` cannot apply twice, so the durable operation protocol is not needed. After an uncertain result the frontend rereads the recipe. The expected next version with the submitted yield and rows means saved; the unchanged version, or 404 for a creation, means not saved and the same draft may be submitted again; anything else is reviewed as a conflict. No recipe request or UUID is kept in browser storage.

Estimate refinements. `currency` equals the settings currency and amounts use the settings `minor_digits`. `recipe_version` is null without a recipe. `ingredient_contribution_minor` equals `selling_price_minor - ingredient_cost_minor` and may be negative. `complete` is true exactly when `missing` is empty; every incomplete estimate has null cost and contribution. Each `missing` entry carries `variant_id`; `ingredient_id` is null for `recipe_missing`. A recipe whose yield no longer equals the variant's current selling format is reported as `recipe_missing`, with its `recipe_version`, until it is saved again for that format. `basis` has one row per recipe ingredient, in recipe order: `{ingredient_id, ingredient_name, base_unit, base_quantity, purchase_id, purchase_line_id, purchased_on, unit_cost, estimated_cost}`. A priced row names the latest purchase basis, the nine-decimal `unit_cost`, and `estimated_cost`, the row amount as a nine-decimal major-currency string calculated from the unrounded receipt basis. An unpriced row has all five of those fields null and a matching `price_missing` entry; it is never zero. The total is the sum of the exact row amounts rounded once, half-up; the frontend displays row amounts and does not re-sum them. The menu list shows only recipe presence from `recipe_id`. A per-variant estimate status in the food list would need an additional backend-derived variant field and is not part of this proposal.

## Planning and Preparation (Phase 7)

`GET /planning?date_from=YYYY-MM-DD&date_to=YYYY-MM-DD` uses inclusive business dates and returns `{id, calculated_at, timezone, period, complete, missing, foods, ingredients, permitted_actions}`. Bound the requested period to 366 days; reject an invalid/larger range with 422. This grouped result is complete for the period, not a paginated list with incomplete totals.

`foods` rows include `variant_id`, name/unit/package snapshots, ordered/prepared/remaining quantities, and `orders: [{order_id, reference, order_item_id, status, ordered_quantity, prepared_quantity, remaining_quantity}]`. Group by variant AND compatible selling-unit/package snapshots so a changed format never merges unlike quantities. Demand quantities follow Confirmed/Preparing/Ready eligibility and remaining counts, including inconsistent Ready records. The backend may use the current reviewed recipe for remaining demand; already-recorded consumption retains historical recipe snapshots.

`ingredients` rows include `ingredient_id`, name, base unit, physical stock, earlier remaining demand, selected remaining demand, signed stock after earlier commitments, earlier shortage, selected period shortage, and cumulative shortage. Use the disjoint-period formulas in the register. Earlier commitments include all eligible outstanding fulfillment before the selected period, including overdue orders, exactly once. Planning never inserts movements or decrements stock. A missing recipe in either earlier or selected demand makes `complete=false`, with affected order/variant links; computed known quantities are a lower bound, not an authoritative complete shopping quantity.

`GET /planning/shopping-list?date_from=...&date_to=...` returns the same period/calculation fields plus `items` with ingredient/base unit, known cumulative shortage, and `complete`. Do not independently round/derive a different list in the frontend. Print the period, units, earlier commitments, and any incomplete warning.

Preparation draft: `{prepared_on, allocations: [{order_id, expected_version, order_item_id, quantity}], consumption: [{ingredient_id, expected_version, quantity, unit}], note?}`. Allocations are positive integers, no repeated item IDs, and cannot exceed each item's remaining quantity. Consumption is explicit actual positive physical quantities with no repeated ingredient IDs; unit compatibility and stock bounds are backend checks. An empty consumption list requires a nonblank explanation for preparation using no tracked ingredients; never silently substitute a recipe estimate for actual usage.

| Method / path | Request | Success |
|---|---|---|
| `POST /preparations/preview` | `{draft}` | 200 Preview with snapshot recipes/cost bases, normalized actual usage, before/after stock, current prepared/remaining quantities, incomplete-cost warnings, and expiry |
| `POST /preparations` | `{preview_id, draft}`, operation key | 201 `{preparation, orders, ingredients}` |
| `GET /preparations/{id}` | None | 200 immutable Preparation |
| `POST /preparations/{id}/correction-preview` | `{reason, allocations: [{order_id, expected_version, order_item_id, delta_quantity}], stock_corrections: [{ingredient_id, expected_version, delta_base_quantity, corrects_movement_id}]}` | 200 before/after prepared/remaining/stock review and warnings |
| `POST /preparations/{id}/corrections` | Identical reviewed fields plus `preview_id`, operation key | 201 `{correction, orders, ingredients}` |

Previews have `id`, `expires_at` (five minutes), bind exact inputs and every order/ingredient/recipe/cost-basis version, and expose missing basis rather than zero cost. Save compares versions, permissions, and stock in one transaction. Reject changed dependencies with no partial preparation. A committed operation replay bypasses revalidation and cannot consume twice. Preparation recording never automatically changes fulfillment status; refresh permissions and allow the separate next status action when quantities are consistent.

Preparation: `{id, prepared_on, allocations, consumption, recipe_snapshots, cost_basis_snapshots, estimated_ingredient_cost_minor, estimate_complete, operation_id, recorded_at, recorded_by}`. Allocations have immutable item/unit snapshots and prepared quantity; consumption has original units, normalized base quantity, ingredient snapshot, and movement ID. Costs may be null when unknown; keep snapshots immutable after recipe/purchase changes.

Phase 7 frontend refinements for the planning read side, proposed for backend agreement. Planning requires the `orders` and `planning` capabilities. `date_from` and `date_to` are sent together or not at all; without them the backend plans for its own business date and reports it in `period: {date_from, date_to}`. A single parameter, a start after the end, a period longer than 366 days, or an unknown parameter is 422. `foods` lists only lines fulfilled inside the period, one row per variant and selling format: `{variant_id, food_name, variant_label, selling_unit, package_contents, ordered_quantity, prepared_quantity, remaining_quantity, orders}`. Row quantities are the sums of its `orders`, each `{order_id, reference, order_item_id, status, ordered_quantity, prepared_quantity, remaining_quantity}` with status `confirmed|preparing|ready` and `remaining_quantity = ordered_quantity - prepared_quantity`. While preparation recording is off, prepared quantities are reported as 0 rather than null. `ingredients` rows are `{ingredient_id, ingredient_name, base_unit, stock_on_hand, earlier_demand, period_demand, stock_after_earlier, earlier_shortage, period_shortage, cumulative_shortage}` as ingredient-quantity strings; `stock_after_earlier` is signed. The frontend verifies the register's formulas on every row: `stock_after_earlier = stock_on_hand - earlier_demand`, `earlier_shortage = max(0, earlier_demand - stock_on_hand)`, `period_shortage = max(0, period_demand - max(0, stock_after_earlier))`, and `cumulative_shortage = max(0, earlier_demand + period_demand - stock_on_hand)`. Earlier demand is every eligible remaining quantity fulfilled before `date_from`, including overdue orders. `missing` entries are `{code: "recipe_missing", variant_id, food_id, food_name, variant_label, orders: [{order_id, reference}]}`, one per variant, for demand in or before the period whose variant has no recipe for the ordered selling format; `food_id` lets the frontend link to the recipe page. `complete` is true exactly when `missing` is empty. `permitted_actions` contains `record_preparation`. The dashboard's preparation summary is this same endpoint called for the dashboard date; there is no separate summary endpoint. `GET /planning/shopping-list` takes the same parameters with the same defaults and validation and returns exactly `{id, calculated_at, timezone, period, complete, missing, items}`. `items` holds only ingredients whose cumulative shortage is greater than zero, as `{ingredient_id, ingredient_name, base_unit, stock_on_hand, earlier_demand, period_demand, cumulative_shortage}`, name ascending; the frontend verifies `cumulative_shortage = earlier_demand + period_demand - stock_on_hand` on each row and rejects a zero or padded row. It prints the backend's list as given and derives nothing itself.

Phase 7 frontend refinements for preparation recording, proposed for backend agreement. Recording requires the `orders`, `planning`, `inventory` and `preparation_recording` capabilities. Each planning order row also carries `order_version`, the version an allocation must quote as `expected_version`; the frontend rejects a row without it. Preview: `{id, expires_at, prepared_on, note, allocations, consumption, recipe_snapshots, cost_basis_snapshots, estimated_ingredient_cost_minor, estimate_complete, currency, minor_digits}`. Preview allocations are `{order_id, reference, order_item_id, variant_id, expected_version, food_name, variant_label, selling_unit, package_contents, ordered_quantity, prepared_before, quantity, prepared_after, remaining_after}` in draft order, with `prepared_after = prepared_before + quantity` and `remaining_after = ordered_quantity - prepared_after >= 0`. Preview consumption is `{ingredient_id, ingredient_name, base_unit, expected_version, quantity, unit, base_quantity, before_quantity, after_quantity}` in draft order; `quantity` and `unit` are as entered, `base_quantity` is the normalized amount, and `after_quantity = before_quantity - base_quantity >= 0`. `recipe_snapshots` has one `{variant_id, recipe_id, recipe_version}` per prepared variant, both null when the variant has no recipe. `cost_basis_snapshots` has one `{ingredient_id, purchase_id, purchase_line_id, purchased_on, unit_cost}` per used ingredient in the same order, all null when it was never purchased. `estimate_complete` is true exactly when every basis is known; otherwise `estimated_ingredient_cost_minor` is null, never zero. The note is returned trimmed. The saved Preparation keeps the same allocation fields without the review-only counts and `expected_version`, and the same consumption fields without `expected_version` plus `stock_movement_id`; it adds `note`, `currency`, `minor_digits`, `operation_id`, `recorded_at` and `recorded_by`. Keeping stock before and after on the record lets the frontend check that each returned ingredient shows the stock the record describes. `POST /preparations` answers `{preparation, orders, ingredients}` with each affected order and ingredient exactly once, moved past the version the draft quoted; its operation has `resource_type: "preparation"`. Validation failures are 422 with field paths under `/draft`, such as `/draft/allocations/0/quantity`, `/draft/consumption/1/unit` and `/draft/note`. A stale order or ingredient version is 409 `version_conflict` with `details.resource_type` of `order` or `ingredient`. Usage beyond physical stock is 409 `insufficient_stock` with a field error on the consumption row's quantity. A missing, expired or changed preview is 409 `quote_stale`. With recording enabled, new orders have `preparation_tracking: "recorded"` and item `prepared_quantity` starting at 0; `record_preparation` is allowed for Confirmed, Preparing and Ready orders with something remaining, and `mark_ready` and `complete` are refused with a reason until nothing remains. `cancellation_requires_stock_acknowledgment` is true once any line has a prepared quantity. An order quote refuses a quantity below the prepared quantity at `/draft/items/{n}/quantity` and the removal of a prepared line at `/draft/items`. A stock movement's `preparation_id` must name a preparation that consumed that ingredient, otherwise 422 at `/preparation_id`; the frontend sends it for waste and correction movements opened from a preparation record, and sends `corrects_movement_id` with the record's consumption movement for corrections only.

Phase 7 frontend refinements for corrections, proposed for backend agreement. The correction preview is `{id, expires_at, preparation_id, reason, allocations, stock_corrections}` with the trimmed reason. Preview allocations are `{order_id, reference, order_item_id, variant_id, expected_version, food_name, variant_label, selling_unit, package_contents, ordered_quantity, prepared_before, delta_quantity, prepared_after, remaining_after}` in request order, with `prepared_after = prepared_before + delta_quantity`, `0 <= prepared_after <= ordered_quantity` and `remaining_after = ordered_quantity - prepared_after`. Preview stock corrections are `{ingredient_id, ingredient_name, base_unit, expected_version, corrects_movement_id, delta_base_quantity, before_quantity, after_quantity}` with `after_quantity = before_quantity + delta_base_quantity >= 0`. A request needs a nonblank reason of at most 2000 characters and at least one nonzero change. An allocation must name a line of this preparation, and its change may not take the count below what this preparation recorded net of its earlier corrections. A stock correction must name an ingredient this preparation consumed and that consumption movement as `corrects_movement_id`. Validation failures are 422 with paths such as `/reason`, `/allocations/0/delta_quantity` and `/stock_corrections/0/corrects_movement_id`; lowering a count on a Ready or Completed order is refused at `/allocations/{n}/delta_quantity`. Stale versions are 409 `version_conflict`, stock below zero is 409 `insufficient_stock` at the row's `delta_base_quantity`, and a missing, expired or changed preview is 409 `quote_stale`. `POST /preparations/{id}/corrections` answers `{correction, orders, ingredients}`; the correction is `{id, preparation_id, reason, allocations, stock_corrections, operation_id, recorded_at, recorded_by}` with the preview's rows minus `expected_version`, and `stock_movement_id` on each stock row. Its movements have type `correction`, the correction's reason, `preparation_id` and `corrects_movement_id`. Its operation has `resource_type: "preparation_correction"`. Addition: `GET /preparations/{id}/corrections` returns `{items: Correction[]}` in recorded order, so the immutable Preparation never changes and its corrections can still be shown beside it.

Corrections are append-only, linked to the original preparation/movements, bounded so prepared quantities remain between zero and ordered quantity, and stock remains nonnegative. Decreasing prepared quantities on an active Ready/Completed order is rejected until an operator resolves the inconsistent fulfillment state; normal staff cannot reverse completed status. Cancelled-order corrections may amend audit quantities/stock but never restore demand. Explicit physical corrections/waste linked to preparation can also use the ingredient-movement workflow when prepared counts are correct. There is no automatic stock return on cancellation or refund.
